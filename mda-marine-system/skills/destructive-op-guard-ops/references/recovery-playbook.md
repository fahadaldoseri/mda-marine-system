# دليل الاستعادة الآمنة

استخدم هذا المرجع بعد وقوع حذف أو استبدال خاطئ، أو عند الحاجة إلى استعادة ملفات محذوفة من التزام سابق. نفّذ الأوامر على نسخة عمل ومجلد تجريبي أولًا، وسجّل قياسًا قبليًا وبعديًا. هذا الدليل لا يكرر إجراءات تماثل الشجرة في [server-repo-parity-ops](../../server-repo-parity-ops/SKILL.md) ولا اشتقاق حالة الأعطال في [fault-closure-ops](../../fault-closure-ops/SKILL.md).

## 1. أوقف العملية وقِس الواقع

لا تعاود تشغيل أداة المزامنة قبل حفظ الحالة:

```bash
git -C "$REPO" status --short
git -C "$REPO" diff --stat
git -C "$REPO" diff --diff-filter=D --name-only HEAD~1 HEAD
```

لا تُدرج محتوى الأسرار في السجل. يكفي عدد الملفات وقائمة المسارات غير الحساسة.

## 2. استعادة ملفات حذفها التزام واحد

هذه هي الصيغة الآمنة الأساسية التي جُرّبت في حادثة ك-269 على النمط نفسه:

```bash
git -C "$REPO" diff --diff-filter=D -z --name-only HEAD~1 HEAD \
  | xargs -0 --no-run-if-empty git -C "$REPO" checkout HEAD~1 --
```

الأفضل استخدام الأداة المرفقة لأنها تستعيد ملفًا في كل مرة وتتحقق من الباقي:

```bash
python3 scripts/safe_restore.py --repo "$REPO" --sha HEAD~1
python3 scripts/safe_restore.py --repo "$REPO" --sha HEAD~1 --apply
git -C "$REPO" diff --stat
git -C "$REPO" status --short
```

لا تنفذ `commit` إلا بعد مراجعة الفرق. أنشئ commit استعادة مستقلًا، ثم اتبع سياسة الفروع وطلب الدمج في المشروع. لا تستخدم `git push --force`، ولا تعِد كتابة تاريخ الفرع الرئيسي.

## 3. استعادة شجرة كاملة بحذر شديد

إذا كانت الاستعادة الكاملة مطلوبة فعلًا، وبعد نسخة احتياطية ومراجعة النطاق فقط:

```bash
git -C "$REPO" read-tree -u --reset "$SHA"
git -C "$REPO" status --short
git -C "$REPO" diff --stat
```

هذا الأمر يغيّر الفهرس وشجرة العمل، لذلك لا تستخدمه كاختصار لاستعادة ملفات قليلة. لا يغير تاريخ الالتزامات بذاته، لكن أي commit تالٍ يجب أن يكون مقصودًا ومراجعًا. أداة `safe_restore.py` لا تستخدم `read-tree` ولا `reset`.

## 4. أخطاء شائعة يجب منعها

- لا تستخدم `xargs` بلا `-0`؛ المسارات العربية أو التي تحتوي مسافات/اقتباسات ستتجزأ.
- مرّر `--` قبل المسارات حتى لا يُفسر اسم يبدأ بشرطة كخيار.
- أمر `git checkout <sha> -- <paths>` الجماعي قد يُجهض كله إذا فشل مسار واحد. نفّذ المسارات واحدًا واحدًا عند الحاجة، أو استخدم `safe_restore.py`.
- لا تعتبر رمز خروج أداة المزامنة وحده دليلًا كافيًا؛ قارن أعداد الملفات وبصماتها قبل/بعد.
- إذا كان التتبع خاطئًا، افحصه أولًا ثم أصلحه صراحةً:

```bash
git -C "$REPO" branch --show-current
git -C "$REPO" rev-parse --abbrev-ref --symbolic-full-name '@{u}'
git -C "$REPO" branch --set-upstream-to=origin/main main
```

لا تطبق أمر ضبط upstream إلا بعد التأكد من أن الفرع المقصود هو `main` وأن `origin/main` هو المرجع الصحيح.

## 5. حادثة ك-269 والحاجز الدائم

وقع الحذف عندما شُغّلت `tools/sync_to_repo.py` بجذر المستودع بدل مجلد `brain`، فحذفت 182 ملفًا خارج نطاقها. الإصلاح المعتمد هو حارس فشل مغلق: يطبع الخطة، ويرفض الحذف إذا تجاوز 20 ملفًا أو خرج عن نطاق المصدر إلا بعلم `--allow-delete`، مع اختبار سلبي في `tests/test_sync_guard.py` (أربع حالات).

بعد الاستعادة، سجّل الدرس في `memory/learning-log.jsonl` بصيغة JSONL، واقترح حاجزًا، ثم شغّل الحاجز فعلًا. لا تسجل إدخالًا مطابقًا موجودًا من قبل.
