# نشر الموقع الثابت والتحقق الحي

نفّذ هذه المهارة عند تجهيز إصدار لموقع ثابت على استضافة Manus، أو عند التحقيق في نشر يرد برمز نجاح لكن قديمًا، أو عند الحاجة إلى إثبات تطابق النسخة المحلية والنسخة الحية. لا تُعدّل مستودع المشروع من داخل أدوات التحقق ولا تنشر تلقائيًا.

## القاعدة الحاكمة

اعتبر النشر عملية ذات قرارين منفصلين. ابنِ وفحّص أولًا، ثم اطلب قرار نشر صريحًا، ثم التزم وادفع مستودع الموقع، ثم نفّذ نشر Manus، ثم تحقّق حيًا. لا تسمح لنجاح البناء أو `HTTP 200` أن يتحول إلى ادعاء نجاح الإصدار.

## التسلسل الإلزامي

1. استنتج `BRAIN_DIR` و`SITE_DIR` من الوسائط أو البيئة أو الجذور المجاورة. مرّر `--brain` و`--site` و`--date` عندما تختلف البنية.
2. ابنِ `dist/` من المصدر، وشغّل فحوص HTML والبيانات والطباعة وسياسة الأسطح.
3. اعرض نتيجة البوابات واطلب قرارًا صريحًا بالنشر. ارفض أي مسار غير مراقب أو موافقة ضمنية.
4. بعد القرار فقط نفّذ في مستودع الموقع `git add` ثم `git commit` ثم `git fetch` و`git push`، وسجّل رقم الالتزام.
5. نفّذ نشر Manus عبر أداة الاستضافة المعتمدة. لا تجعل أي سكربت في هذه المهارة ينفذ النشر نيابة عن المالك.
6. شغّل `bash scripts/check_live.sh --brain ... --site ... --date YYYY-MM-DD --compare`.
7. إذا خرج رمز `2`، اقرأ سجل `logs/live-YYYY-MM-DD.json`، صنّف الفشل، أصلح السبب الجذري في المصدر، ثم قرر إعادة النشر يدويًا وأعد الفحص. لا تقل «نجح» عند فشل أي مسار أو بصمة أو مؤشر إصدار.

اقرأ [دليل التشغيل](references/runbook.md) عند الحاجة إلى تفاصيل الأوامر ومصفوفة المسارات.

## مصفوفة المسارات

أثبت حيًا المسارات السبعة التالية في كل إصدار

- `/` الرئيسية
- `/reports/YYYY-MM-DD.html` صفحة التقرير
- `/additions.html` صفحة الإضافات
- `/sources.html` صفحة المصادر
- `/feed.xml` التغذية
- `/reports/monthly-2026-10.html` اللوحة
- `/reports/cumulative-2026.html` السجل

سجّل لكل مسار رمز HTTP وحجم الجسم وبصمة محلية وحيّة عند استخدام `--compare`. استخدم `curl` لا Python في فحص الاستضافة عندما ترفض الحماية عميل Python.

## قياس الانتشار وإثبات الإصدار

سجّل وقت بدء التحقق، زمن كل محاولة، الزمن الكلي، وعدد المحاولات. استخدم ست محاولات بفاصل 45 ثانية افتراضيًا، واضبط الفاصل في الاختبار فقط. لا تعتبر أول `200` دليلًا كافيًا. أثبت أن جسم صفحة التقرير يحتوي التاريخ المطلوب، وأن المقارنة بالبصمة أو الفرق تثبت النسخة المحلية نفسها. إذا كانت الاستجابة `200` لكن المؤشر قديم أو البصمة مختلفة، فالحالة فاشلة.

## المقارنة المحلية والحيّة

مرّر `--compare` بعد البناء وقبل التسليم. قارن الملفات المحلية المقابلة للمسارات السبعة، وسجّل `local_sha256` و`live_sha256` وأول مسار مختلف. لا تخفِ فرقًا بسبب التخزين المؤقت؛ سجّل الفرق ثم شخّص CDN أو مسار البناء أو الالتزام أو النشر. لا تغيّر HTML الحي أو المحلي يدويًا لمعالجة الفرق.

## لا نشر تلقائي بلا قرار

`check_live.sh` أداة قراءة فقط. لا تحتوي على `git commit` أو `git push` أو نداء `publish`. لا تضف متغيرًا يجعلها تنشر عند الفشل. اجعل قرار إعادة النشر خطوة بشرية أو خطوة مقيّدة في نظام التشغيل الموثق، ثم أعد التحقق.

## حلقة التحسين الذاتي

عند كل عطل، أضف سجلًا يحوي المعرّف والسطح والعرض والسبب الجذري والإصلاح وقاعدة التشديد والاختبار السلبي ورمز الخروج. لا تغلق العطل بعبارة عامة. شغّل `python3 scripts/propose_tightening.py --brain /path/to/brain --output references/proposed-tightening.md`؛ يستخرج أصنافًا من JSONL ويقترح قاعدة واختبارًا سلبيًا لكل صنف. أرفق مخرجه بالمراجعة، ثم أضف الاختبار السلبي إلى البوابة قبل الإعلان عن الإغلاق.

## رموز الخروج

- `0` تحقق حي مثبت لكل المسارات والمؤشر والمقارنة المطلوبة.
- `2` مسار ناقص أو استجابة غير سليمة أو فرق محلي حي أو مؤشر إصدار غير ظاهر أو مدخل ناقص.

سجّل رمز كل تشغيل في تقرير التسليم، واذكر صراحة أي مسار أو نمط مقارنة لم يُختبر.

## مسار بديل مُثبت عند رفض حزمة الجلب من بعيد الموقع (ك-444)

**العَرَض**: خطوة النشر تفشل ورسالة الدفع `non-fast-forward`، وكل أشكال `git fetch` تفشل بـ
`fetch-pack: protocol error: bad pack header` (وسيط/بعيد لا يسلّم الحزمة الكاملة).

**المسار البديل (بلا force وبلا إعادة كتابة تاريخ)**:

1. جلب مُعمّق مُرشَّح — الأصغر حزمةً والأنجح مع الوسيط:
   `git fetch --depth=1 --filter=blob:none --no-tags origin main`
   (يأتي برأس البعيد الحقيقي عبر `git ls-remote origin main` للمقارنة).
2. تأكيد أن الشجرة المحلية نظيفة: `git status --porcelain` = صفر.
3. إنشاء التزام يربط شجرة المحلي برأس البعيد بلا لمس التاريخ:
   `T=$(git rev-parse HEAD^{tree})`
   `C=$(git commit-tree "$T" -p <رأس البعيد> -m "نشر تقرير <التاريخ> (عبر محرّك الكتيب)")`
4. نقل الفرع الرئيسي بأمان (بلا `--hard` وبلا force):
   `git reset --soft "$C"` ثم `git push origin main` — يجب أن يُظهر `..` تقدّمًا سريعًا.
5. إثبات: `git ls-remote origin main` يطابق الالتزام الجديد، ثم إعادة خطوة النشر في الكتيب
   (`runbook.py run --date <التاريخ> --redo D010`) ثم التحقق الحي.

**قياس النجاح**: D010 برمز 0 · `runbook status` كل الخطوات done · القياس الحي يطابق مؤشرات
المحتوى الجديدة (مثال: `data-row`=102 · الاسم الممنوع=0 · النص الخام=0).

**محاذير**: لا `--force`، ولا `git reset --hard`، ولا حذف فرع؛ وإن تعذّر الجلب المُعمّق أصلًا
يُوثَّق العطل كعطل خارجي مع طلب قرار المالك بدل تجاوز البوابة.
