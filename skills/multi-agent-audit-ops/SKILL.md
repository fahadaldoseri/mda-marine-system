# التدقيق متعدد الوكلاء بقياس مستقل

## الغاية

وزّع التدقيق على وكلاء ذوي نطاقات غير متداخلة، وحوّل كل ادعاء إلى قياس يمكن إعادة تشغيله، ولا تقبل عبارة «سليم» أو «مؤكد» بلا أمر ورمز خروج أو رقم. استخدم `scripts/claims_table.py` لإنتاج التصنيف الموحّد، و`templates/audit-report.md` للتقرير النهائي.

## القاعدة الحاكمة

اجعل الدليل القابل لإعادة التشغيل هو أساس الحكم، وميّز بين التشخيص والإصلاح والإغلاق؛ لا ترفع حالة ادعاء أو عيب بلا القياس الذي يثبتها.

## طريقة التنفيذ

ابدأ بتحديد النطاق والملفات، ثم وزّع ملكية الفحص، واجمع القياسات، وبعدها طبّق مسار الإصلاح الخاص بالإصدار المنشور إن انطبق.

## توزيع الوكلاء

أنشئ وكيلًا مستقلًا لكل نطاق، ولا تسمح لوكيل أن يعلن سلامة نطاق وكيل آخر

1. **الواجهة**؛ افحص البنية، التخطيط، القص، الاستجابة، والعناصر المرئية.
2. **الطباعة**؛ افحص PDF، عدد الصفحات، بصمة CSS، الخريطة، مفتاحها، التذييل، والانقسامات.
3. **اللغة**؛ افحص العربية، المصطلحات، الأرقام، RTL/LTR، والاتساق التحريري.
4. **الأسطح والروابط**؛ افحص المسارات المنشورة والروابط والأصول وحالات HTTP أو رموز الأدوات.
5. **الوصول**؛ افحص لوحة المفاتيح، التركيز، النص البديل، العناوين، التباين، وأسماء العناصر المساعدة.

اطلب من كل وكيل ملف ادعاءات JSON منفصلًا يضم معرّفًا فريدًا، ونطاقًا، وادعاءً، وأمر القياس، ورمز الخروج أو رقمًا. اقرأ `references/claim-measurement.md` قبل بناء الملف.

## دورة التدقيق والإصلاح

1. ثبّت نسخة الإدخال ووقت الجولة، ثم اجمع ملفات الادعاءات من الوكلاء دون دمج دليل أحدهم في نطاق آخر.
2. حوّل كل ادعاء إلى قياس قابل للتكرار؛ استخدم أمرًا حقيقيًا مثل مدقق أو اختبار أو طلب HTTP، وسجّل رمز الخروج أو الرقم والعتبة.
3. شغّل جدول الادعاءات

```bash
python3 /home/ubuntu/skills/multi-agent-audit-ops/scripts/claims_table.py /path/to/claims.json
```

صنّف كل صف إلى **مؤكد بقياس** أو **مرفوض بقياس** أو **لم يُتحقق**. إذا حمل الصف `confirmed` بلا قياس صالح، أخرج الرمز 2 وأوقف التقرير؛ لا تحول الادعاء إلى نجاح.

4. سجّل في سجل الأعطال العيوب المؤكدة بقياس فقط، مع السبب الجذري، والقاعدة التي تُشدّد، والاختبار السلبي. لا تصلح عيبًا مرفوضًا أو غير متحقق منه بوصفه عيبًا.
5. أصلح العيوب المؤكدة فقط، ثم شغّل الاختبارات السلبية التي تمنع عودتها.
6. نفّذ **جولة تدقيق ثانية** بالقياسات نفسها، وقارن الصفوف والرموز والأرقام. أبقِ ما لم يُتحقق منه في قسمه ولا تغلقه ادعائيًا.
7. استخرج أصناف الثغرات واقتراحات التشديد

```bash
python3 /home/ubuntu/skills/multi-agent-audit-ops/scripts/propose_tightening.py \
  --root /path/to/brain --log /path/to/brain/audit/faults-raw.jsonl \
  --out /path/to/tightening-proposals.md
```

## ترتيب التقرير

استخدم القالب كما هو، وبالترتيب الإلزامي التالي

1. العيوب المؤكدة.
2. ادعاءات مرفوضة أو مصحّحة.
3. ما ظهر سليمًا.
4. ما لم يُتحقق.
5. خطة الإصلاح بالترتيب.

اربط كل عيب بسجل الأعطال وبقياسه. لا تضع إصلاحًا في الخطة لادعاء لم يثبت عيبه، ولا تضع ادعاءً سليمًا بلا دليل.

## حلقة التحسين الذاتي

اجعل كل ثغرة سلسلة واحدة قابلة للمراجعة؛ السبب الجذري ثم القاعدة المشددة ثم الاختبار السلبي ثم جولة التدقيق الثانية. اعتبر مخرج `propose_tightening.py` اقتراحًا يحتاج اعتمادًا وتنفيذًا، لا دليل إغلاق. أرفق المخرج مع التقرير، واذكر أي وكيل أو سطح لم يُختبر صراحة.


## تدقيق إصدار منشور من المادة الخام (قياس 2026-11-11)

استخدم هذا المسار لمقابلة الإصدار المنشور بمادته الخام، لا بملخصات سابقة. اقرأ `references/measured-inventory-2026-11-11.md` بوصفه سجل أمثلة الجولة؛ فهو يثبت مسارات القياس ولا يدّعي أن الإصلاحات أُغلقت.

1. ثبّت معرّف الإصدار، واجرد ملف الواجهة، سجل الوقائع اليومي، المتنين العربي والإنجليزي، شيفرة المولّد، الصفحة المبنية، والسجلات الحاكمة. مثال الجولة موثق في مرجع الجرد، بما فيه اختلاف بين حقلي مصدر يحتاج حسمًا لا تخمينًا.
2. خصّص لكل ملف مالك تدقيق واحدًا، ثم أنشئ توزيعًا حتميًا بقائمة المسارات عبر `scripts/partition_audit_files.py`. قسّم فحص الجولة بين وكلاء قراءة فقط، ولا تجعل وكيلًا يعيد فحص نطاق زميله.
3. لكل مرشح، سجّل مسار الصفحة المنشورة ورقم السطر والقيمة المقيسة، ثم مسار المصدر الخام ورقم السطر والقيمة الصحيحة، ثم مسار المولّد ورقم سطر الاشتقاق. لا تُثبت عيبًا بلا هذه السلسلة أو بلا مصدر حقيقة محسوم.
4. اكتب السبب الجذري، وأقل إصلاح كلفة وأكبر أثر، والحارس الدائم واختبار الانحدار المقابل. إذا كان العيب مشتركًا بين أسطح، أصلح نقطة الاشتقاق المشتركة بدل رقع كل صفحة.
5. صنّف المرشح إلى مانع مؤكد أو عيب مهم أو إنذار كاذب. ارفض الإنذار الكاذب صراحةً بدليل قياس النفي؛ وإذا لم يوجد قياس، فالحالة «لم يُتحقق» لا «سليم».
6. عند الإصلاح، عيّن وكيل كتابة واحدًا لكل ملف مصدر، واختبر كل عيب على حالة سليمة وأخرى مخالفة. لا تغيّر الصفحة المبنية بدل المولّد أو المصدر الحاكم.
7. بعد إعادة البناء والنشر عبر المسار المعتمد، قِس القيم نفسها على المخرج الحيّ والأسطح المتأثرة، وسجّل قبل/بعد والأمر والمخرج ورمز الخروج. أعد جولة التدقيق بالمقاييس نفسها.
8. أغلق كل عيب على حدة عبر `fault-closure-and-learning-ops`: صف العطل، ودرس السبب الجذري في سجل التعلم، وحاجز يمنع التكرار مع اختبار، وقرار مرقّم بحسب حوكمة المشروع. غياب قياس بعدي أو حاجز فعّال يبقي العيب مفتوحًا.

قواعد مستفادة من القياس تُطبّق بعد حسم المصدر: البلاغ لا يثبت أثرًا أو هجومًا؛ التاريخ الثابت يُشتق من الإصدار؛ معنى المصدر لا يُسمّى بدرجة تحليلية؛ الرقم بلا قراءة رسمية مؤرخة غير قابل للتحقق؛ وإعادة البناء لا تكتمل قبل فحص السطح الناتج.

## ما يجب ألا يحدث

- لا تستبدل المادة الخام بملخص، ولا تدمج دليل وكيل في نطاق آخر.
- لا تترك الملف نفسه بلا مالك واحد للتدقيق والكتابة، ولا تعتبر إنذارًا كاذبًا بلا دليل نفي.
- لا تغلق عيبًا بقياس قبلي فقط، أو ببصمة ملف وحدها، أو بحارس لم يختبر موجبًا وسالبًا.
- لا تصلح `dist/` مباشرة، ولا تنشر خارج المسار المعتمد؛ قياس السطح الحي قراءة فقط بعد نشر مأذون.


## حدود المهارة
هذه المهارة لا تغلق العيوب أو تنشئ الحواجز؛ المهارة الجارة `fault-closure-and-learning-ops` تفعل ذلك.


## الأدوات

- `scripts/partition_audit_files.py` — يوزّع قائمة ملفات على وكلاء دون تكرار مسار؛ قراءة فقط ورمز 2 عند مدخل غير صالح.
- `scripts/claims_table.py` — يصنّف الادعاءات بحسب القياس؛ يمنع الادعاء المؤكد بلا دليل صالح.
- `scripts/propose_tightening.py` — يستخرج اقتراحات تشديد؛ مخرجه اقتراح وليس إثبات إغلاق.
