# 90-automation — سلسلة التشغيل اليومي

**الغرض:** الترتيب الملزم لتنفيذ التقرير الصباحي من جمع المصادر حتى النشر.
**يُقرأ مع:** كل الأقسام، وINDEX.md قبل البدء
**ممنوعات:** لا يُنشر تقرير لم يجتز بوابة 60-validation.
**مراجع تفصيلية:** appendices/web-delivery.md و`/home/ubuntu/seawatch/generator/` (المصدر الواحد للمولّد)
**آخر تعديل:** 2026-10-12 · **المصدر:** من تفاصيل المهمة المجدولة وأدوات التشغيل

---
## أ1 — الترتيب الملزم للتشغيل الصباحي

1. اقرأ `INDEX.md` ثم الأقسام المطلوبة في هذه السلسلة.
2. افحص المصادر السبعة والثلاثين حسب طرق الوصول في 10-sources، وسجّل لكل مصدر حالته.
3. ابنِ التقرير وفق 30-structure، واملأ كتل 40-blocks من المصادر فقط.
4. طبّق 50-analysis: افصل الحقيقة عن التقدير، واذكر درجة الثقة، وراجع الاتساق.
5. **التحليل الاستخباري:** شغّل `tools/intel_self_review.py` واقرأ `memory/intel-adaptation.md`، ثم اكتب قسم «التحليل الاستخباري» وفق 55-intelligence (ح1–ح12): الافتراضات · ACH مصغّر · مؤشرات التحذير المبكر · تقييم دقة تقديرات الأمس · وسم الأسلوب.
6. مرّر 60-validation: بوابة اللغة آليًا، ومراجعة المصطلحات، وحاجز التصنيف، وبوابة التحليل الاستخباري (ف5).
7. سلّم وفق 70-delivery: نص داخل المحادثة، ورابط الموقع الدائم، وPDF عند الطلب فقط.
8. أضف وقائع اليوم إلى الدفتر التراكمي، وأعد توليد اللوحة الشهرية، وسجّل تقديرات القسم في `memory/intel-estimates.jsonl`.
9. سجّل أي تصحيح في `memory/learning-log.jsonl` عبر `memory/record_learning.py`، وقيّم دقة تقديرات الأمس داخل القسم (ح5).

## أ2 — أوامر التنفيذ المعتمدة

```bash
# بناء صفحة التقرير (المصدر الواحد للمولّد؛ وweb/build_report.py رابط رمزي إليه)
python3 /home/ubuntu/seawatch/generator/build_report.py --md reports/<التاريخ>-sectioned.md --meta web/meta/<التاريخ>.json --out /tmp/report-<التاريخ>.html
# فحص الصفحة (يشمل فحص الوسوم المهرَّبة)
python3 /home/ubuntu/seawatch/generator/verify.py /tmp/report-<التاريخ>.html
# فحص المصادر واللغة قبل التسليم
python3 validators/check_sources_37_browser.py
python3 validators/check_language.py reports/<التاريخ>-sectioned.md
# المدقق المانع لبنية التقرير
python3 validators/validate_report.py web/meta/<التاريخ>.json --md reports/<التاريخ>-sectioned.md
# بوابة التحليل الاستخباري (ف5) — قبل بناء الصفحة
python3 validators/check_intel.py reports/<التاريخ>-sectioned.md web/meta/<التاريخ>.json
# التكيّف الذاتي للقسم قبل الكتابة (ح12)، وقياس دقة التقديرات (ح10)
python3 tools/intel_self_review.py --date <التاريخ>
python3 tools/estimate_accuracy.py
# تحديث الموقع الدائم ونشره
python3 /home/ubuntu/seawatch/generator/sync_from_brain.py --date <التاريخ>
python3 /home/ubuntu/seawatch/generator/build_site.py --check   # يفشل عند أي وسم مهرَّب أو صفحة ناقصة
cd /home/ubuntu/seawatch && git add -A && git commit -m "إصدار <التاريخ>" && git fetch origin main && git push origin main
# ثم النشر عبر أداة الاستضافة: webdev.config {"method":"POST","path":"publish","body":{}}
```

## أ3 — قواعد الأتمتة

- الجدولة اليومية عند 07:00 بتوقيت البحرين، ومراقبة التغذيات للتنبيه الفوري عند تطوّر أمني.
- لا يُعاد نشر تقرير منشور، ويُفحص وجود تقرير اليوم لمنع التكرار.
- عند فشل خطوة، يُسجَّل السبب ويُستأنف من الخطوة التالية دون إسقاط التقرير كله.

## أ4 — سلسلة التنفيذ المفصّلة

> منقول من مهارة marine-news-brain في المرحلة الثانية (2026-10-12) — نص أصلي بلا تغيير.

1. اقرأ آخر تقرير محفوظ، ثم افحص وجود تقرير اليوم لمنع التكرار.
2. اقرأ `appendices/historical-baseline.md`، ثم استخدم دفتر الأحداث التاريخي لمطابقة الخلفية والاتجاهات، وأضف الخلفية الأقدم فقط إذا بقي أثرها مؤثرًا.
3. اجمع أخبار آخر 24 ساعة وفق UTC، وأضف الخلفية الأقدم فقط إذا بقي أثرها مؤثرًا.
4. افحص قائمة المصادر الـ37 في `appendices/sources-37.md`، وسجّل حالة كل مصدر: فُحص، لا مستجد، تعذر الوصول، أو استُشهد به.
5. اتبع أقسام واهتمامات التقرير في `sections/30-structure.md` دون إسقاط قسم مؤثر أو إضافة حشو.
6. صنّف كل واقعة: هجوم مؤكد، تفاعل عسكري، حادث غير محسوم، احتمال ملاحي/تقني، أو خلفية.
7. قارِن الأرقام بالحالة السابقة، واحسب الفروقات والزمن المنقضي آليًا.
8. قيّم المصدر واستقلاليته؛ لا ترفع الثقة بسبب نسخ لغوية أو ناقلين لبيان واحد.
9. ابنِ التحليل: الوقائع، المؤشرات، التوزيع الجغرافي للوقائع، مستوى التهديد، المجهولات، والاحتمالات.
10. راجع القاموس في `references/terminology.md` وقواعد التحقق في `references/validation.md`.
11. نفّذ بوابة التحقق قبل التسليم.
12. سلّم النص العربي داخل المحادثة، وولّد نسخة صفحة الويب وارفعها لتسليم رابط HTTPS مباشر وفق `appendices/web-delivery.md`. لا تسلّم الرابط قبل نجاح الفحص الآلي. لا تنشئ PDF إلا بطلب صريح؛ عند الطلب أنشئ نسخة جاهزة للطباعة من التقرير المعتمد.
13. اقرأ الدروس المؤكدة من `/home/ubuntu/brain-marine-news/memory/learning-log.jsonl`، ثم نفّذ فحص تراجع للتأكد من عدم عودة الأخطاء السابقة.
14. سجّل كل تصحيح مستخدم أو خطأ متكرر عبر `memory/record_learning.py` بعد تصنيفه، ولا ترفع الدرس إلى قاعدة ملزمة دون دليل كافٍ.

## الخط اليومي الموحّد (معتمد 13 أكتوبر 2026 — دمج كامل)

يُنفَّذ **قبل** كتابة التقرير، وبالترتيب:
```
# 0) ضمان البيئة (إلزامي) — سبب اعتماده: حادثة 13 أكتوبر 2026
bash /home/ubuntu/brain-marine-news/tools/ensure_devserver.sh 3000        # يعيد خادم المعاينة إن كان متوقفًا
python3 /home/ubuntu/brain-marine-news/tools/preflight_check.py $(date -u +%F)   # فحص ما قبل التشغيل
# 1) الخط الموحّد — يُستدعى بـbash لا بـpython3
bash /home/ubuntu/brain-marine-news/tools/daily_pipeline.sh $(date -u +%F)
```
- قوائم المدخلات **دائمة في المستودع**: `watchlist/ofac-targets.txt` (أسماء السفن والوسطاء) و`watchlist/original-sources.txt` (روابط البلاغات الرسمية). لا تُستخدم ملفات `/tmp` لأنها تُمحى.
- **لا تُكمل** إذا أظهر فحص ما قبل التشغيل أي **فشل** (رمز خروجه 1)؛ التحذيرات تُذكر في التقرير ولا توقف العمل.
- الخط يكتب سجلًا `logs/pipeline-<التاريخ>.log` وعلامة نجاح `logs/pipeline-<التاريخ>.json`؛ **لا تسلّم** إصدارًا بلا علامة `overall = ok`.
**ترتيب التنفيذ الإلزامي:**
1. **التغذيات** (`tools/check_feeds.py`) → إنذار مبكر لمستجدات آخر 24 ساعة من 38 تغذية.
2. **فحص OFAC** (`tools/ofac_screen.py`) → لكل سفينة/وسيط؛ النتيجة (تطابق/مراجعة يدوية/لا تطابق/تعذر) تُكتب في التقرير.
3. **حفظ الأصول الرسمية** (`tools/archive_originals.py`) → HTML/PDF + UTC + `sha256` في `archive/originals/<التاريخ>/manifest.json`.
4. **دمج الذاكرة التراكمية** (`tools/merge_ledger_daily.py`) → ملف اليوم يُدمج في `cumulative-2026/event-ledger-master.json` وتُبنى `appendices/event-code-map.json`، ويُنسخ الدفتر إلى `sources/ledger.json` في الموقع.
5. كتابة التقرير، ثم بناء الصفحة، ثم **مزامنة النسخة الاحتياطية** (`bash tools/sync_backup.sh`)، ثم الحفظ والنشر الآلي.
   - النسخة الاحتياطية تُكتب في `/home/ubuntu/seawatch/brain-backup` داخل مستودع الموقع، فتُحفظ مع نقطة الاستعادة.
   - **لا يُستخدم `rsync`** لأنه غير مثبّت في البيئة (كانت المزامنة تفشل بصمت)؛ الأداة تعتمد `cp` فقط وتتحقق من حداثة تقرير اليوم وأدوات التشغيل.
**قاعدة الرموز:** رمز الحدث (MN-…) يُمنح مرة واحدة ومعناه ثابت؛ ولا يُسلَّم إصدار فيه رمز لا يُحلّ في خريطة الرموز. **لا تُسلَّم** نسخة بلا دمج الذاكرة (علامة الخط تُظهر `ledger_merge`).
**ممنوع:** تسليم تقرير فيه سفينة بلا نتيجة فحص OFAC، أو بلاغ رسمي مستشهد به بلا أصل محفوظ أو سبب تعذر مكتوب، أو بلا علامة نجاح للخط اليومي.
